Aula 3 — Componentização
Correção dos exercícios

Cada exercício abaixo tem a demonstração funcionando, o HTML e o JavaScript da solução. O código exibido é exatamente o que está rodando na página.

Fluxo de dados: dados descem por props, eventos sobem por emits.

Regra de ouro: o filho nunca altera uma prop. Quem muda o dado é o pai.

Aqui todos os exercícios estão em uma única página, por isso cada um monta o seu app em um #app1, #app2… Na entrega dos alunos, cada exercício tem seu próprio index.html e app.js, com #app.

Exercício 1 — Meu primeiro componente

Componente saudacao-usuario com um <h2> "Olá, bem-vindo ao curso!", usado três vezes.

Código
  • O componente é registrado com app.component() antes de app.mount().
  • Cada uso da tag cria uma instância independente do componente.

Exercício 2 — Saudação personalizada

O componente recebe a prop nome e exibe "Olá, {nome}!". Três usos, três nomes.

Código
  • Sem dois-pontos (nome="Ana"), o valor chega como texto fixo.
  • Para usar uma variável ou número, seria :nome="variavel".

Exercício 3 — Cartão de produto

Componente cartao-produto com as props nome, preco e emEstoque, mostrando o preço como "R$ 0,00" e "Disponível" ou "Esgotado".

Código
  • :preco="249.9" e :em-estoque="true" usam dois-pontos: são expressões JavaScript, então chegam como número e booleano.
  • No HTML a prop emEstoque é escrita em kebab-case: em-estoque.
  • O preço é formatado em uma computed com toLocaleString("pt-BR", …).

Exercício 4 — Validando props

Mesmas props do exercício 3, agora com validação. Dois usos propositalmente errados: um sem nome e outro com preço inválido. Os avisos do Vue aparecem no console e também na lista abaixo.

  • {{ aviso }}
Código

O que cada aviso significa:

AvisoExplicação
Missing required prop: "nome" A prop nome tem required: true, mas o segundo cartão foi usado sem informá-la.
Invalid prop: type check failed for prop "preco" A prop espera Number, mas recebeu o texto "barato". Atenção: mesmo preco="10", sem dois-pontos, também geraria este aviso, porque chega como texto. O correto é :preco="10".
  • Nenhuma das duas situações quebra a página: a validação só avisa, e só no build de desenvolvimento do Vue.
  • emEstoque ausente não gera aviso: o valor padrão true é aplicado (por isso o primeiro cartão aparece como disponível).

Exercício 5 — Lista de tarefas

O pai tem uma lista de pelo menos quatro tarefas (id, texto, feita) e exibe cada uma com tarefa-item. As concluídas aparecem riscadas.

Código
  • O :key="t.id" é obrigatório no v-for e deve ser um identificador estável, não o índice.
  • O id fica no pai, usado só como chave; o filho recebe apenas o que precisa mostrar.
  • O risco vem de uma classe CSS aplicada com :class="{ feita: feita }".

Exercício 6 — Concluindo tarefas

Ao clicar em uma tarefa, ela alterna entre feita e pendente. O filho não altera props: quem muda o dado é o pai.

Código
  • Filho: no clique, avisa com $emit("alternar"). Ele não sabe o que o pai fará com o aviso.
  • Pai: escuta com @alternar="alternar(t.id)", encontra a tarefa e inverte feita.
  • O erro clássico seria o filho fazer this.feita = !this.feita: o Vue avisa no console que props são somente leitura.

Exercício 7 — Botão reutilizável

Componente botao-acao que recebe um rótulo e avisa o pai ao ser clicado. O pai mostra a pontuação e usa o mesmo botão para "+1", "+10" e "Zerar".

Pontuação: {{ pontos }}

Código
  • O botão só sabe o rótulo e que precisa avisar quando for clicado. O que cada clique significa é decisão do pai.
  • Um componente, três comportamentos: a diferença está só no que o pai faz ao escutar @acionar.

Exercício 8 — Contador com limite

Componente contador-controle com "−", o valor e "+". O valor fica no pai, que não aceita menos que 0 nem mais que 10; no limite, o botão correspondente fica desativado.

Código
  • O dado (valor) mora no pai. O filho recebe o valor e os limites por props e só pede para aumentar ou diminuir.
  • O :disabled deixa a interface coerente, mas a regra de verdade está nos métodos do pai: mesmo que alguém dispare o evento por outro caminho, o limite continua valendo.

Exercício 9 — Adicionando tarefas

Componente nova-tarefa com campo de texto e botão "Adicionar". O texto vai ao pai, que inclui a tarefa na lista. O campo é limpo depois, e textos vazios são ignorados.

Código
  • O texto digitado (v-model) é estado do filho, porque só importa enquanto a pessoa digita. Ao clicar, ele sai pelo evento: $emit("adicionar", texto).
  • trim() evita tarefas feitas só de espaços; depois de enviar, this.texto = "" limpa o campo.
  • O pai cria o objeto da tarefa, com id próprio (proximoId), e dá push na lista.
  • @keyup.enter permite adicionar também com a tecla Enter.

Exercício 10 — Desafio: mini app de tarefas

Aplicação completa com nova-tarefa, tarefa-item (concluir e remover) e resumo-tarefas ("X de Y tarefas concluídas"). Só o pai guarda a lista, todas as props têm validação, todo evento é declarado em emits, o total de concluídas vem de computed e o console fica sem avisos.

Nenhuma tarefa ainda. Digite acima e clique em Adicionar.

Código

Árvore de componentes:

App (componente pai)
  dados:    tarefas, proximoId
  computed: concluidas
  │
  ├── nova-tarefa
  │     ↑ emits:  adicionar(texto)
  │
  ├── tarefa-item   (um para cada tarefa, com v-for)
  │     ↓ props:  texto, feita
  │     ↑ emits:  alternar, remover
  │
  └── resumo-tarefas
        ↓ props:  concluidas, total

Resumo do fluxo:

ComponenteRecebe do pai (props)Avisa o pai (emits)O pai faz
nova-tarefanadaadicionar(texto)push de uma nova tarefa em tarefas
tarefa-itemtexto, feitaalternar, removerinverte feita ou filtra a tarefa para fora da lista
resumo-tarefasconcluidas, totalnenhumsó entrega os números
  • concluidas é uma computed: se recalcula sozinha sempre que uma tarefa muda ou é removida, sem precisar de um contador paralelo para manter em dia.
  • Checkbox do filho usa :checked="feita" (só leitura) e @change para avisar. Não há v-model em prop, que seria uma alteração de prop disfarçada.
  • resumo-tarefas não tem emits porque não dispara nenhum evento.
